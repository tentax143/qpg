## 🔴 Retrieval

- [x] **#14 — Class 11 generated ungrounded (embedding dimension mismatch).** Every Class 11 section produced "0 chars" of context and was generated with no NCERT grounding. Root cause: the whole Class 11 corpus (Chemistry, Physics, Mathematics, Computer Science, English Core, Social Science) had been embedded with the OpenRouter/nemotron model (**2048-dim**) and stored in the `default` collection, but the query path always embeds with Ollama `nomic-embed-text` (**768-dim**) and reads that same collection — so ChromaDB rejected every query (`Embedding dimension 768 does not match collection dimensionality 2048`). Other classes were Ollama-embedded and unaffected. **Fix:** new `manage.py fix_embedding_dims` command re-embeds the stored chunk text of every mismatched `default` collection with the local model (reads text + computes vectors *before* deleting, aborts on bad vectors). Repaired **18 collections / ~15.7k chunks** across `shared` + `school_1` + `school_2`; verified all 768-dim and real retrieval returns NCERT content. **Defense-in-depth:** `embeddings.query` now detects a dim mismatch, logs one actionable line (`fix with manage.py fix_embedding_dims --apply`) and returns empty instead of silently shipping an ungrounded paper. Files: `core/management/commands/fix_embedding_dims.py` (new), `core/embeddings.py`.

## 🟠 Re-render

- [x] **#15 — Re-render times out and errors the page.** The synchronous re-render endpoints (`rerender`, AI-edit / restore via `_render_paper_from_stored_data`) ran `materialize_images`, which **regenerates images via external APIs** for anything not cached. Worst case per uncached image: OpenAI 180s × 2 attempts + Together 120s + Pollinations 120s ≈ **10 minutes**, blocking the web request until the server/proxy times out → error on the page. Images are already generated and cached (by prompt-hash) during the async Celery generation, so re-render should only *reuse* them. **Fix:** added a `cache_only` mode (new `ImageNotCached` exception) threaded `generate_ai_image → materialize_images → _render_paper_from_data`; the synchronous endpoints now pass `cache_only=True` — cached images are reused, uncached ones are skipped, and **no external image call is ever made in a web request**. (`render_edited_docx` already used `render_docx` directly and made no image calls.) Tests `RerenderImageCacheTest` assert no network call + graceful skip. Files: `core/generator.py`, `api/views.py`. *Note: the async generation task still generates fresh images (`cache_only=False`) — unchanged.*

## 🟢 Chapter coverage / weightage

- [x] **#16 — Full-portion tests: chapters chosen randomly by the LLM, no weighting, no coverage guarantee.** Previously each section was told "spread across all N chapters, ~1 each" and the model picked chapters itself — sections didn't coordinate (popular chapters repeated, many got nothing) and CBSE weightage only affected *context retrieval*, never the question count. **Fix (CBSE blueprint method):** `plan_chapter_allocation` now deterministically assigns each section's question slots to specific chapters — weighted by `UNIT_MARKS_WEIGHTS` where known, **uniform where not** (so it works for every class today) — using a `weight / (1 + already_covered)` greedy that's **coordinated across the whole paper** (later sections fill earlier gaps before any chapter repeats). The exact distribution is named in the prompt ("Electrochemistry: 4, Solutions: 3, …") and each question is tagged with its chapter. A **coverage audit** (`audit_chapter_coverage`) reports planned-vs-covered chapters and surfaces gaps on the "Completed ⚠" badge; `manage.py audit_papers` shows it too. Smoke test: Class 12 Chemistry covered 11/14 chapters in 13 questions with the heaviest unit getting the extra; Class 11 (uniform) spread 10 MCQs across 10 distinct chapters. Tests `ChapterAllocationTest` + `ChapterCoverageAuditTest`. Files: `core/section_generator.py`, `core/paper_audit.py`, `core/tasks.py`, `core/generator.py` (strip `_chapter_plan` at render), `core/management/commands/audit_papers.py`. *Caveat: `UNIT_MARKS_WEIGHTS` is currently Class-12 + Science only; other classes get even (uniform) coverage until their official CBSE unit weightages are added — no code change needed to upgrade them.*

## 🔴 Question-type adherence

- [x] **#17 — Sections generate the wrong question type (e.g. a "Short Answer" section comes back full of MCQs).** Two compounding causes: (1) the section prompt's STRICT RULES are MCQ-centric and never stated the section's *required* type or forbade others, so uniform non-MCQ sections (SA/VSA/LA) drifted to MCQs; (2) the count-based type validation only ran for *mixed* sections (`expected_counts` built from per-type dicts) — **uniform sections had no type check at all**, so well-formed MCQs rendered straight into a Short-Answer section (and malformed ones thrashed → partial). **Fix (three layers):** (a) an explicit `QUESTION TYPE — MANDATORY` prompt block names the exact allowed type(s) and JSON `type` value, and for SA/VSA/LA adds "written-answer — do NOT include options"; (b) `validate_section_output` now builds an **allowed-category set** for uniform sections and rejects any foreign type during generation ("only SA allowed, but got MCQ×2") → drives a retry; (c) **final safety net** — `enforce_section_question_types` runs after generation (before numbering/render) and **removes any wrong-type question that still slipped through** (the partial-emit path ships whatever it has after exhausting retries). It uses COARSE categories so legitimate subtypes are never dropped (assertion-reason→MCQ, map-based→SA, image/source→CBQ) and keeps unclassifiable types; drops are logged + recorded on `_dropped_wrong_type` and surfaced by the marks/coverage audits. Also fixed the linked truncation: `_per_q_tokens` MCQ budget 180→**280** (16-MCQ sections truncated at ~12 because `500+16×180=3380` hit the output cap → the Section A marks shortfall). Tests `SectionTypeEnforcementTest` (8 cases). Files: `core/section_generator.py`, `core/generator.py` (strip `_dropped_wrong_type` at render).

## 🟠 Images

- [x] **#18 — A second, irrelevant image appears on image-based CBQs (e.g. an org chart on a Chemistry diagram question).** The CBQ already got its real image during generation (ImageFinder → stored as the section's `image_path`, rendered once). But at render time, `process_question` saw the question tagged `image_based` with no explicit `image_prompt` and **derived an image prompt from the stem text** — and the stem was the generic *"Observe the diagram carefully and answer the following questions:"*. Feeding that pointer (not a description) to the image generator produced a meaningless generic "diagram" (the CEO/Manager org chart) as a second image. **Fix:** added `_is_generic_image_stem` — the stem is only turned into an image prompt when it actually *describes* a visual; generic "observe/study/refer to the diagram/source… answer the following" pointers are skipped (the real image still comes from `image_path` / an explicit `image_prompt`). Applied to both render paths. Tests `ImageStemGuardTest`. Files: `core/generator.py`.

## 🔴 Under-production & misleading coverage

- [x] **#20 — Sections silently ship SHORT on count (e.g. Section A 8/16 MCQs → −8 marks), and the coverage badge over-reported gaps.** Investigated paper 64 (Class 11 Chemistry, Board pattern): Section A produced **8 valid MCQs and just stopped** (all correct type/marks, `_partial`), repeated across all 3 attempts — the base model under-delivers on large uniform batches, and there was **no top-up** to fill the gap, so the section shipped half-empty. *Why it still "passed":* per-section count/marks **are** validated and retried during generation, but when the model can't satisfy after `MAX_SECTION_RETRIES`, the section ships partial rather than failing the whole paper — the marks audit then surfaces it on the ⚠ badge (warn, don't block, by design). **Fix:** `_top_up_short_section` — after retries, a section that is merely short on count gets **one focused follow-up call** for exactly the missing questions, on the still-uncovered chapters, forbidding repeats; strictly **additive** (only valid, correctly-typed, non-duplicate questions, never more than the shortfall — can't worsen the section), then re-validated to clear `_partial` if whole. Mixed-marks/CBQ/passage/map sections are left to the normal path. Tests `SectionTopUpTest`. **(Follow-up — Section A 15/16, MCQ + Assertion-Reason):** two further fixes. (1) The top-up originally required a *single* category and so skipped a `['MCQ','Assertion-Reason']` Section A — it now accepts any of the section's declared types as long as the section is **uniform-marks** (an AR question is a valid fill for a 1-mark slot), with concept-overlap dedup (`_concept_overlap > 0.6`) on the added questions since they bypass the V5 chain. (2) Root cause of *that* shortfall was **output truncation**, not the model stopping early: `[Mantle] out=4980 tokens … [JSON-Salvage] Recovered 15 … from truncated output`. AR questions carry the full A/R statements + 4 long standard options + explanation, so 16 don't fit `500+16×280=4980`. `estimate_token_budget` now sizes AR-containing uniform sections at **400/q** (→ 6900 for a 16-q Section A; pure-MCQ unchanged at 4980), so all 16 fit in one call and the top-up is just the safety net. **Also fixed the misleading coverage number:** the badge said "Chapter coverage 21/26" — but **26 was per-section chapter *slots*, not chapters** (9 chapters × 5 sections → repeats), and it cried "Section C: Thermodynamics missing" even when Thermodynamics appeared in another section. `audit_chapter_coverage` now reports **distinct paper-wide** coverage (a chapter answered anywhere counts as covered); re-audited paper 64 = **9/9 chapters covered, no warning** (only the real marks shortfall remains). Per-section slot detail kept in `audit_papers` (`slot_planned`/`slot_covered`). Tests updated in `ChapterCoverageAuditTest`. Files: `core/section_generator.py`, `core/paper_audit.py`, `core/generator.py` (strip `_topped_up`), `core/management/commands/audit_papers.py`. *Note: the pattern mismatch the user suspected (Class-12 pattern → Class-11 questions) is **not** the cause — the chapters are genuinely the 9 Class-11 Chemistry chapters; the pattern only sets section shape, which is class-agnostic.*

## 🟢 Team usage

- [x] **#21 — Team-usage page resets each user's tokens/cost when papers are deleted.** The `school_user_usage` endpoint recomputed every teacher's tokens/cost by aggregating their **live** `QuestionPaper` rows — so deleting a paper erased its owner's usage from the page. Real impact: School 1's persistent cumulative counter showed **1,548,060 tokens / ₹1,273 across 61 papers**, but the per-user table summed to only **171,495 / ₹152** because 57 papers had been deleted. The School keeps an atomic cumulative counter; there was no per-user equivalent. **Fix:** new append-only **`UsageEvent`** model (`user`, `school`, `paper_id`, `kind`, `input_tokens`, `output_tokens`, `cost`, `created_at`) — `generate_paper_task` logs one event per generation (a regenerate re-runs the task → another event), so each teacher's **all-time and monthly** figures now survive paper deletion. The endpoint aggregates these events instead of live papers; `total_papers` is the persistent generated-count (consistent with the school's `total_papers_generated`), with a new `current_papers` showing how many they still own. A **data migration backfills** one event per surviving paper (stamped with the paper's own `created_at`, so monthly stays correct), guarded to never double-count. Tests `TeamUsagePersistenceTest` (persists after deletion + monthly windowing). Files: `core/models.py` (`UsageEvent` + `.record()`), `core/migrations/0025_usageevent.py`, `core/migrations/0026_backfill_usage_events.py`, `core/tasks.py`, `api/admin_views.py`, `frontend/src/app/team-usage/page.js`. *Scope (per the chosen option): only paper generation is logged; re-render / AI-edit token+image costs are still not attributed (deferred). Deleted papers from before this change can't be re-attributed per user — that usage remains only in the school counter — but everything going forward persists.*

## 🔴 Sections shrink after validation

- [x] **#22 — A section silently ships short when the type-enforcer (or dedup) removes a question *after* validation passed.** Paper 66 (Class 11 Computer Science, PT-1, 80m) audited **68/80**: Section A 18/20, Section D 4/6. Root cause (confirmed from `paper_data`): the work orders correctly asked for 20 and 6 (the `_chapter_plan` lengths were 20 and 6), generation produced the full count, but **2 questions in each section came out as type "SA"** (recorded in `_dropped_wrong_type`: A=Q8,Q15; D=Q5,Q6) and were correctly removed by `enforce_section_question_types` (#17). Because that enforcer — and the V5 semantic-dedup pass — run *after* per-section validation has already passed, the section never went `_partial` and the top-up (#20) never fired (it only runs inside the per-section retry loop). So the section just shipped short. (Contributing upstream gap: the individual LA/CBQ path logs validation errors but proceeds, so a mis-typed LA isn't regenerated.) **Fix:** `generate_paper_parallel` now runs a **refill pass right after `enforce_section_question_types`** — any section left below its work order's count is topped back up via `_top_up_short_section` (correct-type, non-duplicate, capped at the shortfall) before renumbering. This closes the gap for *both* causes (type-drop and dedup-trim), regardless of which path generated the section. Files: `core/section_generator.py`. *Note: paper 66 itself predates this fix; regenerate it (worker must be running the new code) to get the full 20/6.*

## 🟢 Hindi & Tamil support

- [x] **#23 — Enable Tamil & Hindi papers (rendering + in-language generation).** Before: only **Tamil** rendering was wired (subject/text detection → `Latha` font); **Hindi/Devanagari had no font handling** (rendered as boxes outside MS Word desktop), and **no path told the model to write in the target language** — so a "Hindi"/"Tamil" paper came back in English. **Changes:** (1) Rendering generalised — `_pick_script_font(subject, questions)` picks **Latha** for Tamil and **Nirmala UI** for Devanagari (Hindi/Sanskrit), by subject name or by scanning the generated text (`has_devanagari_text`, U+0900–U+097F); the run-level setter and document styles now take that font (the working Tamil path is unchanged). (2) `_language_directive(subject)` injects a MANDATORY "write everything in {Devanagari/Tamil}" block into **all three generation prompts** — the parallel section prompt, the per-question LA/CBQ prompt, and the single-prompt fallback. (3) Retrieval needs no change: `embeddings.query` filters by `where={"unit": chapter}`, so uploaded Hindi/Tamil chunks are pulled from the correct chapter regardless of query language (only within-chapter ranking is degraded by the English embedder). Tests `LanguageSupportTest` (4). Files: `core/generator.py`, `core/section_generator.py`. **How to test:** upload materials under subject "Hindi"/"Tamil", generate, open the DOCX. **Caveats:** the reader's PC needs the font (Latha / Nirmala UI — standard on Windows); semantic retrieval ranking is still English-embedding-based (chapter filter saves it); the unused `render_pdf` (reportlab/Helvetica) path would NOT render Indic — DOCX is the only active output.

## 🟢 Intelligent material ingestion

- [x] **#24 — Smart upload: auto-detect chapter names + split a whole-book PDF into chapters.** Before, the unit name was just the filename (bulk) or typed by hand, so a randomly-named PDF gave a junk unit. Two **opt-in** capabilities (both default OFF → existing uploads are byte-for-byte unchanged, zero launch risk), run in the async ingest tasks so no web request is blocked: **(1) Auto-detect chapter names** — reads each PDF's first pages, asks the validation LLM which chapter it is, **snaps the answer to the official CBSE chapter catalog** (`UNIT_MARKS_WEIGHTS`) when one matches, and updates both the ingested unit and the `Material` row. **(2) Whole-book auto-split** — upload ONE textbook PDF → `detect_book_chapters` finds per-chapter page ranges from the PDF's **bookmarks/outline** (fallback: scan pages for "Chapter N"/"Unit N" headings), names each (LLM + catalog), and ingests each chapter's pages as its own unit (one `Material` row per chapter, all referencing the uploaded file; the placeholder row is reused as chapter 1 so the file is never orphaned). Falls back to a single auto-named unit if it can't find 2+ chapters. New `core/material_intel.py` (all detection is best-effort — never raises into the caller); `embeddings.ingest_pdf` gained a `page_range` arg; `ingest_material_task` gained `auto_name`; new `split_book_task`; two toggles on the upload page (`auto_detect_units`, `split_book`). Tests `MaterialIntelTest` (5). Files: `core/material_intel.py` (new), `core/embeddings.py`, `core/tasks.py`, `api/views.py`, `frontend/src/app/materials/upload/page.js`. *No migration. Caveats: detection needs real PDF text (scanned/image PDFs still extract poorly — no OCR); catalog-snapping only helps subjects that have a catalog (others get the LLM's free-form name); ~1 small LLM call per file/chapter.*

## 🟢 HTML book import (solves Tamil/Hindi extraction)

- [x] **#25 — Import a whole textbook from an HTML URL → auto-split into chapters.** The TN-schools (and similar) textbooks are served as a single clean HTML page — far better than PDF for Indic scripts (proper Unicode, real heading tags, no OCR, no PyPDF2 ligature mangling). Validated against the real Class-10 Tamil book: **31 clean chapters** ("இயல் ஒன்று", …), 505 K chars of Unicode Tamil, zero OCR. `_clean_name` now strips zero-width chars (ZWNJ/ZWJ/BOM). Opt-in (only fires when a URL is pasted) — no existing behaviour changes. No new deps (`requests`/`beautifulsoup4`/`lxml` already present), no migration (reused `Material.metadata`). Tests `MaterialIntelTest` (HTML splitting + no-heading fallback). Files: `core/material_intel.py`, `core/embeddings.py` (`ingest_text`), `core/tasks.py` (`ingest_url_task`), `api/views.py` (`import_url`), `frontend/src/app/materials/upload/page.js` (URL field). *Minor: a "Table of Contents" heading can appear as a unit — delete it.
