## 🔴 Retrieval

- [x] **#14 — Class 11 generated ungrounded (embedding dimension mismatch).** Every Class 11 section produced "0 chars" of context and was generated with no NCERT grounding. Root cause: the whole Class 11 corpus (Chemistry, Physics, Mathematics, Computer Science, English Core, Social Science) had been embedded with the OpenRouter/nemotron model (**2048-dim**) and stored in the `default` collection, but the query path always embeds with Ollama `nomic-embed-text` (**768-dim**) and reads that same collection — so ChromaDB rejected every query (`Embedding dimension 768 does not match collection dimensionality 2048`). Other classes were Ollama-embedded and unaffected. **Fix:** new `manage.py fix_embedding_dims` command re-embeds the stored chunk text of every mismatched `default` collection with the local model (reads text + computes vectors *before* deleting, aborts on bad vectors). Repaired **18 collections / ~15.7k chunks** across `shared` + `school_1` + `school_2`; verified all 768-dim and real retrieval returns NCERT content. **Defense-in-depth:** `embeddings.query` now detects a dim mismatch, logs one actionable line (`fix with manage.py fix_embedding_dims --apply`) and returns empty instead of silently shipping an ungrounded paper. Files: `core/management/commands/fix_embedding_dims.py` (new), `core/embeddings.py`.

## 🟢 Chapter coverage / weightage

- [x] **#16 — Full-portion tests: chapters chosen randomly by the LLM, no weighting, no coverage guarantee.** Previously each section was told "spread across all N chapters, ~1 each" and the model picked chapters itself — sections didn't coordinate (popular chapters repeated, many got nothing) and CBSE weightage only affected *context retrieval*, never the question count. **Fix (CBSE blueprint method):** `plan_chapter_allocation` now deterministically assigns each section's question slots to specific chapters — weighted by `UNIT_MARKS_WEIGHTS` where known, **uniform where not** (so it works for every class today) — using a `weight / (1 + already_covered)` greedy that's **coordinated across the whole paper** (later sections fill earlier gaps before any chapter repeats). The exact distribution is named in the prompt ("Electrochemistry: 4, Solutions: 3, …") and each question is tagged with its chapter. A **coverage audit** (`audit_chapter_coverage`) reports planned-vs-covered chapters and surfaces gaps on the "Completed ⚠" badge; `manage.py audit_papers` shows it too. Smoke test: Class 12 Chemistry covered 11/14 chapters in 13 questions with the heaviest unit getting the extra; Class 11 (uniform) spread 10 MCQs across 10 distinct chapters. Tests `ChapterAllocationTest` + `ChapterCoverageAuditTest`. Files: `core/section_generator.py`, `core/paper_audit.py`, `core/tasks.py`, `core/generator.py` (strip `_chapter_plan` at render), `core/management/commands/audit_papers.py`. *Caveat: `UNIT_MARKS_WEIGHTS` is currently Class-12 + Science only; other classes get even (uniform) coverage until their official CBSE unit weightages are added — no code change needed to upgrade them.*

## 🔴 Question-type adherence

- [x] **#17 — Sections generate the wrong question type (e.g. a "Short Answer" section comes back full of MCQs).** Two compounding causes: (1) the section prompt's STRICT RULES are MCQ-centric and never stated the section's *required* type or forbade others, so uniform non-MCQ sections (SA/VSA/LA) drifted to MCQs; (2) the count-based type validation only ran for *mixed* sections (`expected_counts` built from per-type dicts) — **uniform sections had no type check at all**, so well-formed MCQs rendered straight into a Short-Answer section (and malformed ones thrashed → partial). **Fix (three layers):** (a) an explicit `QUESTION TYPE — MANDATORY` prompt block names the exact allowed type(s) and JSON `type` value, and for SA/VSA/LA adds "written-answer — do NOT include options"; (b) `validate_section_output` now builds an **allowed-category set** for uniform sections and rejects any foreign type during generation ("only SA allowed, but got MCQ×2") → drives a retry; (c) **final safety net** — `enforce_section_question_types` runs after generation (before numbering/render) and **removes any wrong-type question that still slipped through** (the partial-emit path ships whatever it has after exhausting retries). It uses COARSE categories so legitimate subtypes are never dropped (assertion-reason→MCQ, map-based→SA, image/source→CBQ) and keeps unclassifiable types; drops are logged + recorded on `_dropped_wrong_type` and surfaced by the marks/coverage audits. Also fixed the linked truncation: `_per_q_tokens` MCQ budget 180→**280** (16-MCQ sections truncated at ~12 because `500+16×180=3380` hit the output cap → the Section A marks shortfall). Tests `SectionTypeEnforcementTest` (8 cases). Files: `core/section_generator.py`, `core/generator.py` (strip `_dropped_wrong_type` at render).

## 🔴 Under-production & misleading coverage

- [x] **#20 — Sections silently ship SHORT on count (e.g. Section A 8/16 MCQs → −8 marks), and the coverage badge over-reported gaps.** Investigated paper 64 (Class 11 Chemistry, Board pattern): Section A produced **8 valid MCQs and just stopped** (all correct type/marks, `_partial`), repeated across all 3 attempts — the base model under-delivers on large uniform batches, and there was **no top-up** to fill the gap, so the section shipped half-empty. *Why it still "passed":* per-section count/marks **are** validated and retried during generation, but when the model can't satisfy after `MAX_SECTION_RETRIES`, the section ships partial rather than failing the whole paper — the marks audit then surfaces it on the ⚠ badge (warn, don't block, by design). **Fix:** `_top_up_short_section` — after retries, a section that is merely short on count gets **one focused follow-up call** for exactly the missing questions, on the still-uncovered chapters, forbidding repeats; strictly **additive** (only valid, correctly-typed, non-duplicate questions, never more than the shortfall — can't worsen the section), then re-validated to clear `_partial` if whole. Mixed-marks/CBQ/passage/map sections are left to the normal path. Tests `SectionTopUpTest`. **(Follow-up — Section A 15/16, MCQ + Assertion-Reason):** two further fixes. (1) The top-up originally required a *single* category and so skipped a `['MCQ','Assertion-Reason']` Section A — it now accepts any of the section's declared types as long as the section is **uniform-marks** (an AR question is a valid fill for a 1-mark slot), with concept-overlap dedup (`_concept_overlap > 0.6`) on the added questions since they bypass the V5 chain. (2) Root cause of *that* shortfall was **output truncation**, not the model stopping early: `[Mantle] out=4980 tokens … [JSON-Salvage] Recovered 15 … from truncated output`. AR questions carry the full A/R statements + 4 long standard options + explanation, so 16 don't fit `500+16×280=4980`. `estimate_token_budget` now sizes AR-containing uniform sections at **400/q** (→ 6900 for a 16-q Section A; pure-MCQ unchanged at 4980), so all 16 fit in one call and the top-up is just the safety net. **Also fixed the misleading coverage number:** the badge said "Chapter coverage 21/26" — but **26 was per-section chapter *slots*, not chapters** (9 chapters × 5 sections → repeats), and it cried "Section C: Thermodynamics missing" even when Thermodynamics appeared in another section. `audit_chapter_coverage` now reports **distinct paper-wide** coverage (a chapter answered anywhere counts as covered); re-audited paper 64 = **9/9 chapters covered, no warning** (only the real marks shortfall remains). Per-section slot detail kept in `audit_papers` (`slot_planned`/`slot_covered`). Tests updated in `ChapterCoverageAuditTest`. Files: `core/section_generator.py`, `core/paper_audit.py`, `core/generator.py` (strip `_topped_up`), `core/management/commands/audit_papers.py`. *Note: the pattern mismatch the user suspected (Class-12 pattern → Class-11 questions) is **not** the cause — the chapters are genuinely the 9 Class-11 Chemistry chapters; the pattern only sets section shape, which is class-agnostic.*

## 🟢 AI pattern generation

- [x] **#26 — "AI generate pattern" spins forever.** Reported by teachers: the create-pattern page loads and never resolves. Three independent causes, all fixed. **(1) Patterns queued behind papers.** `generate_pattern_task` (one LLM call, ~30-60 s) shared the single default Celery queue with `generate_paper_task` (many calls, up to the 25-min hard limit) — and the Windows worker runs `--pool=solo`, i.e. **strictly one task at a time**, so `CELERY_WORKER_CONCURRENCY = 4` was dead config. Any teacher clicking "AI generate" while *any* paper anywhere on the instance was building waited for that paper to finish. Patterns now route to their own `patterns` queue (`CELERY_TASK_ROUTES`) served by a second worker (`--pool=threads --concurrency=4 -Q patterns`); the papers worker also drains `patterns` (`-Q celery,patterns`) so a single-worker deploy still works exactly as before instead of stranding jobs in an unconsumed queue. **(2) Nothing ever timed out.** The task had no time limit, and `converse()` derives its read window from `max_tokens` — at 8000 tokens that is a 300 s read × 3 retries = **15 minutes of one wedged call**. Pattern calls now pass an explicit `(10, 150)` timeout (`PATTERN_CALL_TIMEOUT`), and the task carries `soft_time_limit=8 min / time_limit=9 min`; a timeout fails **without retrying** (a retry only holds the queue behind a job that cannot finish). **(3) Orphaned patterns were immortal.** Papers have `reap_stale_papers`; patterns had no equivalent, so a pattern whose task evaporated in a worker/broker restart sat at `queued`/`generating` **forever** while the page polled it every 3 s with **no deadline**. New `reap_stale_patterns` (12 min queued / 10 min generating) runs on the polled detail endpoint, so the very poll that used to spin forever is the one that resolves it. Also: the task no longer flips to `failed` *between* retries (the UI showed an error while a retry that would have succeeded was still scheduled), and the front end now shows **queued vs generating**, an elapsed clock, and a 10-min deadline with an actionable message instead of an eternal spinner. Refactored the shared normalise → validate → repair → warn → derive block out of the task into `core.tasks.build_validated_sections` so the seeder path below is held to the identical contract. - [x] **#26b — Consolidated the two workers into one (operator request).** The #26 fix shipped as two workers (`--pool=solo` for papers + a threads worker for `patterns`) because that changed nothing about how papers execute. In practice two terminal windows is a burden nobody maintains, and a half-started stack is worse than the original bug — found exactly that live: only the patterns worker was up, so **nothing was consuming `celery`** and the next paper any teacher generated would have hung forever. Now ONE worker: `celery -A qpg worker --loglevel=info --pool=threads -Q celery,patterns`. `--pool=solo` is what caused the original bug (one task at a time regardless of any setting), so the threads pool is load-bearing, not cosmetic. Three supporting changes were required to make a single concurrent worker actually safe rather than just simpler:
  - **Global cap on in-flight LLM calls** (`mantle_client.MAX_CONCURRENT_CALLS`, env `QPG_MAX_CONCURRENT_LLM_CALLS`, default 6). Each paper already fans out `MAX_PARALLEL_SECTIONS = 3` sections at once, so 6 concurrent papers would want **18 simultaneous Mantle calls** — and on the current single live key that is a 429 storm. A 429 does not merely slow a paper: `_top_up_short_section` / the section retries can still come up short and the section ships partial, i.e. questions silently vanish from the paper. A `BoundedSemaphore` around the request itself (NOT around the retry backoff sleep, which would hold a slot while doing nothing) bounds total concurrency for the whole process independent of task count. Floor is `MAX_PARALLEL_SECTIONS` so a lone paper never throttles itself; saturation is logged (`[Mantle] WAIT ... all 6 call slots busy`) so a slow paper is distinguishable from a slow model. Tests `LlmConcurrencyCapTest` (4) — including slot release on exception, since a leaked slot would ratchet the process to zero throughput.
  - **`CELERY_WORKER_CONCURRENCY` 4 → 6**, and the run command deliberately passes **no** `--concurrency` so settings stay the single source of truth. 6 rather than 4 because papers hold a slot for minutes and patterns for seconds — the headroom is what keeps a slot free for a pattern while several papers build. Note this setting was dead config until now; `--pool=solo` ignored it, which is also why papers serialised across schools.
  - **`temp_questions.json` → `temp_questions_<thread>.json`.** A fixed path meant whichever concurrent paper finished last clobbered the others' debug dump — useless exactly when concurrency makes it interesting. Still gitignored via `temp_*`.

  The `patterns` queue is **kept** even though one worker drains both: it costs nothing and preserves the option to split patterns back onto a dedicated worker (`-Q patterns`) with no code change. *Accepted cost, documented in `run_commands.txt`: `mantle_client._run_stats` is a process-global reset per task, so concurrent papers interleave their token/cost totals. The per-call `[Mantle] OK` lines stay accurate and stage-stamped, so individual calls remain attributable — only the per-paper summary is approximate under load. Making it exact needs a task-scoped context threaded through the section ThreadPoolExecutor; not worth it for an observability number.* Files: `core/mantle_client.py`, `core/section_generator.py`, `qpg/settings.py`, `run_commands.txt`.

## 🟢 Blueprints made real

- [x] **#28 — Blueprints now mean something: a per-question unit plan over a pattern.** Before this, `blueprint_id` was validated in `api/views.py`, stored in `paper.gen_params`, passed into `generate_paper_task(paper_id, blueprint_id=None, ...)` — **and never read again**; the word did not appear anywhere in that function's body. Live DB: 1 `ExamBlueprint` + 2 `BlueprintTemplate` rows against 80 patterns, 1 of 14 papers ever carrying a blueprint_id, and `DetailedBlueprintTemplate` with **no database table at all**, so `blueprints/detailed-builder` (856 lines) could never save. The concept was designed, half-built and abandoned, while the manual promised teachers "precise control over coverage" it could not deliver.

  **The insight that made this small:** the generator already assigns one chapter per printed question — `SectionWorkOrder.chapter_plan`, filled by `plan_chapter_allocation()` weighted by CBSE unit marks. A blueprint is simply the teacher **overriding that allocation**, so the feature is an injection point, not new machinery. New `section_generator.apply_unit_map()` runs immediately after `plan_chapter_allocation` and applies two layers: section-wide units (restrict the section's candidate chapters and re-allocate) then individual question pins on top. Anything unmapped keeps its automatic allocation — constraining 3 questions must never require filling in all 38.

  - **Keyed by printed qnum, never by position.** `generate_count` can exceed the printed slot count on attempt-N-of-M sections (`section_generator.py`), so indexing `chapter_plan` by a slot's ordinal would silently pin the wrong unit to the wrong question. Test `test_attempt_n_of_m_section_does_not_misassign` locks this.
  - **Per-question precision in the prompt.** The section chapter block only ever stated a *distribution* (`Counter(wo.chapter_plan)`) — enough for automatic allocation, useless for "Q7 specifically must be Optics". The per-slot spec block already carried `TOPIC:`/`format:` per question, so pinned questions now also carry `| CHAPTER: draw this question from "X" ONLY`.
  - **Topic-vs-chapter conflict.** Patterns imported from a CBSE sample paper carry a per-slot `topic` lifted from that paper. Pinning a different chapter produced a prompt stating both ("draw from Optics" + "TOPIC: Electrostatics") and left the model to guess. A topic that is itself a rival *chapter name* is now dropped in favour of the teacher's pin; a topic naming a *skill* within a chapter ("Resistance", "Homophones") is complementary and kept.
  - **Chapters union, not replace.** A pinned unit is added to the paper's chapter set so retrieval actually has material for it, and the teacher's own tick-boxes are never silently dropped. A pinned unit with **no uploaded material** is logged as a warning — those questions generate ungrounded, which is a real misconfiguration, not something to swallow.
  - **Guards on attachment.** `_resolve_blueprint` refuses a `template_<id>` (structure, not units — the old form), a blueprint with an empty map, and critically a blueprint **built for a different pattern** (its qnums address different questions). The generate page now re-fetches the blueprint list per selected pattern so that choice is never offered in the first place, and `get_blueprints` no longer lists BlueprintTemplates or empty blueprints — offering a teacher an option that provably does nothing is how the original confusion started.

  Model: `ExamBlueprint` gains `pattern` FK + `unit_map` + `name` (migration `0051`, additive — existing rows keep their `blueprint` JSON and are listed in the UI as legacy to clean up). API: `pattern` filter, `mapped_questions`/`units_used` on the serializer, serializer validation rejecting a unit map with no pattern, and `GET /patterns/<id>/blueprint-scaffold/` returning the pattern's printed questions **plus** the available units in one call — computing `section_id` with the same `_section_id_from_name` the generator uses, because a mismatch there would let blueprints save fine and then quietly fail to apply. Frontend: new `blueprints/plan` builder (pick pattern → real questions load → per-question unit dropdown, with "apply to all" per section), rewritten list grouped by pattern, and the four legacy pages (`detailed-builder`, `create-template`, `ai-create`, `create-exam`) plus `edit`/`template-edit` reduced to redirects — **2244 lines → 489**. Tests: `UnitMapModelTest`, `ApplyUnitMapTest`, `ResolveBlueprintTest`, `BlueprintScaffoldApiTest`, `BlueprintSerializerTest` (34 new).
